# MailMind AI — codebase review, August 2026

A full-stack audit taken at commit `eb329eb` on `feature/facet-classification`: what is built, what
is wrong, what is missing, and what is left before this is a product you can use daily and
eventually share.

**Method.** Every claim below was checked against the code, not against the documentation. The test
suites were run (API 297 passed / 17 skipped across 30 files; web 66 passed across 14 files;
Playwright 6 passed), the build was run, and the migration set was compared against the Prisma
schema and the Supabase copies.

**Scale.** ~24.3k lines of TypeScript across five workspaces, 18 migrations, 45 test files.

---

## 1. Summary

Two findings dominate everything else.

1. **There are two complete filing engines in this repository, they contradict each other, and the
   one running unattended every fifteen minutes is the one you retired.**
2. **The application cannot be operated from a browser.** Connecting Gmail, syncing, running
   automation, and reviewing held decisions all exist in the API and in the HTTP client, and no
   screen calls any of them.

Neither is a code-quality problem. The code is, in most places, better than it needs to be. Both are
_wiring_ problems — capability that exists and is not reachable.

| Area                  | State                                                                                       |
| --------------------- | ------------------------------------------------------------------------------------------- |
| Security architecture | Strong. Real trust boundary, encrypted tokens, forced RLS, separated OAuth flows            |
| Database              | Strong. 18 migrations, schema/Supabase copies in sync, invariants in constraints            |
| Long-running work     | Strong. Leases, checkpoints, heartbeats, `202` + poll, resumable by construction            |
| ML integration        | Strong design, unmeasured. No evaluation harness, uncalibrated confidence                   |
| API surface           | Incomplete. The facet pipeline has no routes at all                                         |
| Frontend              | Incomplete. Three screens; the operating controls were removed and never replaced           |
| Shareability          | Blocked. Restricted OAuth scope, free-tier model terms, no legal pages, no account deletion |

## 2. What is genuinely well built

Recorded first, because a review that only lists faults is not an accurate review.

**The trust boundary is real, not aspirational.** No `VITE_`-prefixed secret exists anywhere. Google
tokens are AES-GCM encrypted with a stored key version. OAuth state is hashed, single-use,
purpose-bound and expiring, with PKCE, and identity login and Gmail consent use genuinely separate
callbacks. Signing in cannot grant Gmail access, which is the promise the landing page makes.

**Database hygiene is excellent.** All 18 migrations have matching flat Supabase copies under the
same timestamp. RLS is `enable`d _and_ `force`d, and privileges are revoked from
`public`/`anon`/`authenticated`, on every application table — including the two newest,
`message_facets` and `facet_pivot_settings`. Domain invariants live in check constraints rather than
only in code: the kebab-case shape of a facet value, the "a decided facet carries a confidence and
an undecided one carries none" pairing, the `user_labels` depth/path trigger.

**Long-running work is done properly.** Account-scoped expiring leases, checkpoints, `activity_runs`
with a heartbeat and `RUN_ABANDONED` reclamation of runs whose process died, external calls placed
outside database transactions, and `202` + poll instead of a held connection. `STOPPED` is modelled
as a first-class ending rather than a failure. This is the part most projects get wrong and this one
does not.

**The Gemini integration is careful.** One shared paced/retried JSON client, so the free tier's
per-minute quota is respected across features rather than per feature. `responseSchema` constrains
generation _and_ Zod validates the result afterwards, with key, count and duplicate checks. The
system prompt states explicitly that every field is untrusted data and instructions inside a subject
line must never be followed. Temperature 0. Cost is computed from deliberately over-stated paid
rates so the budget cap trips early rather than late.

**The honesty in the comments is a real asset.** The `message_facets` migration records that 85.9% of
the mailbox came back `NONE` and that this was _not_ because the classifier was wrong — it was being
asked a question with no right answer. That is the kind of note that prevents a future rewrite from
repeating the mistake.

## 3. Critical — two competing filing engines

|              | Legacy taxonomy engine                                    | Facet engine                                                                            |
| ------------ | --------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Code         | `features/automation/automation.service.ts` (1,547 lines) | `facet-classification.service.ts`, `labels/pivot.service.ts`, `facet-filing.service.ts` |
| Vocabulary   | leaves of an approved tree                                | `entity` + `domain` + `intent`, pivoted into folders                                    |
| Gmail apply  | `applyLabel` — **additive**                               | `applyExclusiveLabel` — one label or none                                               |
| Reachable by | `POST /api/automation/run` **and the scheduler**          | **8 `tsx` CLI scripts. No routes, no controller, no UI.**                               |

Both write `automation_message_actions`. Both mutate `MailMind/*` Gmail labels.
`AUTOMATION_ENABLED` defaults to `true` and `startAutomationScheduler` polls every
`AUTOMATION_POLL_INTERVAL_MINUTES` (15 by default).

So on any account that ever approved a taxonomy plan, the scheduler will silently re-file mail the
facet pivot filed, using the retired vocabulary, through an additive apply that can leave a message
wearing two MailMind labels at once. Commit `847c977` fixed the two _rule_ systems undoing each
other; the two _filing_ systems still can.

> **This is a live operational hazard, not design debt.** Until the engines are unified, set
> `AUTOMATION_ENABLED=false` on the deployed API.

The facet design is the better one and should win: it costs no output tokens on prose nobody reads,
its apply is exclusive by construction, a message's classification survives a re-pivot without a
single re-classification, and it is the direct answer to the 85.9% `NONE` failure the tree caused.

## 4. Critical — the browser cannot operate the application

`apps/web/src/services/http.ts` defines the methods. No component calls them.

| Capability                 | Client method                                                            | Called by a component?                            |
| -------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------- |
| Connect Gmail              | `getBackendRedirectUrl('/integrations/google/connect')`                  | **No** — exposed on `AuthContext`, never rendered |
| Initial / incremental sync | `initialGmailSync`, `incrementalGmailSync`                               | **No**                                            |
| Initialize Gmail labels    | `initializeGmailLabels`                                                  | **No**                                            |
| Run automation             | `runAutomation`, `getAutomationStatus`                                   | **No**                                            |
| Review queue               | `getAutomationReview`, `approveAutomationReview`, `skipAutomationReview` | **No**                                            |
| Rename / delete a folder   | `renameLabel`, `deleteLabel`                                             | **No**                                            |
| Anything facet or pivot    | —                                                                        | **No client method exists**                       |

The real first-run path today is: sign in → `/sorted` (empty) → `/approve` → _Propose folders_ →
`409`, because Gmail was never connected and no mail was ever synced.

The three-screen rebuild (`6446220`) removed the Dashboard, Connections and Settings screens, and
the capabilities went with them rather than being redistributed. `GET /api/automation/gaps` and
`POST /api/auth/tutorial/complete` are backend features with no consumer at all, and the
`account_scoped_tutorial` migration exists for a tutorial that no longer has a UI.

## 5. Machine-learning integration

### 5.1 What is right and worth keeping

**Deriving `entity` in code rather than asking a model** (`label-discovery/entity.ts`) is the single
best decision in the ML layer. A brand is a fact about the envelope, not a judgement. It costs
nothing, cannot hallucinate, and the alias table handles the case that would otherwise produce two
folders for one brand (`redditmail.com` → `reddit`). The display-name table means a folder is spelled
`GitHub` and `LinkedIn`, not `Github` and `Linkedin`.

**Rules before AI.** `learned_classification_patterns` holds literal `SENDER_DOMAIN` /
`SENDER_ADDRESS` / `SUBJECT_CONTAINS` matches — never regular expressions, because the values come
from an untrusted model and are replayed against every message. Most mail therefore costs zero
tokens. Planner rules are authoritative; learned rules must clear a confidence and a sample floor;
a sender domain that turns out to feed two folders is deactivated rather than flip-flopping.

**Per-axis failure.** An invalid value is discarded for _that facet_, not for the message, and
`UNKNOWN` applies to one axis. A message can be `finance` + unknown intent and still be filed by its
domain. Under a single tree, not knowing one thing about a message meant knowing nothing about it.

**Exactly-once and resumable by construction.** The `message_facets` row _is_ the checkpoint, keyed
by an `input_hash` over the message and the prompt version. A run stopped by a spent quota resumes
where it left off; no message is classified twice.

**Confidence is the weakest facet the folder actually rests on** — counting only the facets the
message was placed by. A message that landed at depth 1 under `["entity", "intent"]` was placed by
its entity alone, so an uncertain intent is not grounds to hold it for review. That is a subtle and
correct piece of reasoning.

### 5.2 Gaps, in priority order

**1 — No evaluation harness, so no change can be shown to help.** There is no labelled ground-truth
set, no accuracy/precision/recall, no per-facet confusion matrix. `scripts/report-facets.ts` prints
_distributions_, which is not correctness: a classifier that assigns `newsletter` to everything
produces a perfectly plausible distribution. Every prompt and vocabulary change is currently shipped
on judgement alone. **This is the highest-value missing piece in the ML layer.**

_Fix:_ hand-label ~300 stratified messages once, store them as a checked-in fixture, and add a
script that reports precision/recall per facet value and a confusion matrix. Gate it on
`prompt_version` so a bump re-runs it.

**2 — Confidence is the model's self-report and is uncalibrated.**
`AUTOMATION_CONFIDENCE_THRESHOLD=0.8` is a guess against an unmeasured distribution. Without a
reliability curve — of the decisions the model called 0.8, how many were right? — that number is
choosing the review-queue volume by accident. The golden set from (1) produces this curve for free.

**3 — The vocabulary is a checked-in constant.** `label-discovery/facets.ts` holds the domains and
intents "the mailbox owner approved on 2026-08-21". `facet-vocabulary.ts` (474 lines) can design one
from real evidence, but the result is never persisted per account. **Multi-user is structurally
blocked here**, independently of any auth work: a second user gets a stranger's taxonomy.

_Fix:_ a `facet_vocabularies` table keyed by connected account, written by an approve step that
mirrors the existing plan → confirm flow.

**4 — Prompt caching is claimed but not earned.** The comment in `facet-classifier.ts` says keeping
the vocabulary in `systemInstruction` "is what makes the prompt cacheable". No `cachedContent` is
ever created, so `cachedContentTokenCount` reads `0` and the cost model's 1/10th cached-input rate
is never applied. Either create an explicit cached context or drop the claim.

**5 — Throughput is left on the table.** `AUTOMATION_BATCH_SIZE=10` at
`GEMINI_MIN_REQUEST_INTERVAL_MS=4000`, one request in flight. The client's own comment measures
~7 requests/minute against a 15/minute cap. The answer is bigger batches or two concurrent requests,
not a shorter interval — the comment says so and the configuration has not followed.

**6 — `prompt_version` is stored and nothing acts on a bump.** No golden-set regression run, no
re-classification trigger. The column is currently documentation.

## 6. Security

| #   | Finding                                                                                                                                                                                                                                                                                                                                                        | Severity           |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| S1  | **`gmail.modify` is a Google _restricted_ scope.** Sharing outside your OAuth test users requires app verification **and an annual CASA Tier 2 security assessment**, plus a live privacy policy, terms of service, in-app data deletion, and a demo video. `/privacy` and `/terms` render a `LegalPlaceholder`; `/support` and `/data-deletion` do not exist. | **Blocks sharing** |
| S2  | **The Gemini free tier may use submitted content to improve Google's products.** Correctly documented in `gemini.client.ts` and correctly scoped to single-user personal use. A paid tier is a precondition for anyone else's mail.                                                                                                                            | **Blocks sharing** |
| S3  | **The SPA ships no security headers.** `vercel.json` sets only a history rewrite — no CSP, HSTS, `frame-ancestors`, `Referrer-Policy`, `Permissions-Policy`, or `X-Content-Type-Options`. Helmet covers API responses only, and an API's headers do not protect the document.                                                                                  | High               |
| S4  | **Rate limiting is in-memory.** `express-rate-limit` uses its default `MemoryStore`. The architecture doc claims multiple instances can share one database; with two Render instances every limit effectively doubles, and a restart clears them. Either use a shared store or state the single-instance constraint in the docs.                               | Medium             |
| S5  | **No account deletion.** There is no `DELETE /api/auth/me`. Required by Google's restricted-scope policy and expected by anyone you share this with.                                                                                                                                                                                                           | Medium             |
| S6  | CI's `push` branch list is stale (no `feature/facet-classification`); Playwright E2E never runs in CI; dead `DYNAMIC_LABEL_*` variables remain in the CI environment.                                                                                                                                                                                          | Low                |
| S7  | No Dependabot or Renovate. The audit gate is `--audit-level=high` and production-only.                                                                                                                                                                                                                                                                         | Low                |

Nothing was found that leaks a secret, mishandles a token, or lets one account read another's data.
The security work that _is_ present is well done; what is missing is the perimeter around the
browser and the paperwork around the scope.

## 7. Efficiency and cleanup

- `automation.service.ts` at 1,547 lines is the retired engine. Removing it is the single largest
  available simplification and also removes the §3 hazard.
- **Dead dependencies in `apps/web`:** `react-hook-form`, `@hookform/resolvers`, and `@mailmind/ui`
  are imported by nothing. `packages/ui/src/button.tsx` is styled in Tailwind slate and matches no
  theme in the product.
- `apps/web/src/components/ConfirmDialog.tsx` is imported by nothing.
- `index.css` is ~3,600 lines for five public pages; roughly half its selectors belong to screens
  that were deleted (`dashboard-*`, `labels-*`, `automation-*`, `classification-*`, `connection-*`,
  `tutorial-*`). Removing them is safe and would meaningfully shrink the CSS bundle.
- The `account_scoped_tutorial` migration and `completeTutorial` endpoint have no UI.

## 8. What is left, in order

### Phase A — make it usable by you

No Google verification needed; this is the largest value for the least risk.

1. **Retire the legacy engine.** Point `POST /api/automation/run` and the scheduler at
   `facetFilingService`. Delete `automation.service.ts`'s classification path. Until then,
   `AUTOMATION_ENABLED=false`.
2. **Give facets an HTTP surface.** `POST /api/facets/classify` (202 + run id),
   `GET`/`PUT /api/facets/pivot`, `GET /api/facets/pivot/plan`, `GET /api/facets/pivot/view`,
   `POST /api/facets/pivot/apply`, `POST /api/facets/file`. The services already expose exactly
   these shapes — this is controllers, Zod schemas, routes and tests, not new logic.
3. **Restore the missing screens.** A **Setup** screen (connect Gmail, initial sync, live progress),
   a **Review** screen for the `REVIEW_REQUIRED` queue, and a **Pivot** screen that previews the tree
   before it touches Gmail. `buildPivot` is already a pure function of the facet rows, which is what
   makes the preview cheap.

### Phase B — make it trustworthy

4. Evaluation harness: labelled golden set, per-facet precision/recall, a reliability curve to set
   the confidence threshold from data rather than from a guess, and a regression run gated on
   `prompt_version`.
5. Real prompt caching, larger batches, and the dead-CSS/dead-dependency cleanup.

### Phase C — make it shareable

6. Per-account facet vocabulary; drop the checked-in constant.
7. Security headers on the SPA, a shared rate-limit store, account deletion, real privacy and terms
   pages, `/support`, `/data-deletion`.
8. Move to a paid Gemini tier, then apply for Google OAuth verification and CASA Tier 2.

Phases A and B are entirely within your control. Phase C is where the calendar stops being yours —
CASA assessment turnaround is measured in weeks, so start it only once A and B are settled.
